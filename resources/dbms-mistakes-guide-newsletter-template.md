A DBMS assignment can lose marks even when the SQL runs successfully. The most common problems often come from unclear requirements, weak schema design, incorrect relationships, incomplete testing, or documentation that does not explain the solution.

We published a practical guide to help you identify and fix these problems before submission.

### What the guide covers

The guide explains how to avoid mistakes involving:

- Requirements analysis
- Primary keys and foreign keys
- Relationship cardinality
- Entity relationship diagrams
- Database normalization
- Data types and constraints
- `INNER JOIN` and `LEFT JOIN`
- `WHERE`, `GROUP BY`, and `HAVING`
- Duplicate rows and incorrect use of `DISTINCT`
- `NULL` values
- Edge-case testing
- SQL dialect differences
- Transactions and indexes
- Project documentation
- DBMS viva preparation
- Protecting sensitive information

### Read the guide

[Read: DBMS Assignment Mistakes That Can Cost You Marks](https://github.com/remysterling-ship-it/sql-database-learning/blob/main/resources/dbms-assignment-mistakes-that-cost-marks.md)

### Need additional guidance?

If you are unsure about a relationship, join, normalization decision, or query result, [AssignmentDude](https://assignmentdude.com/) is an additional educational resource for SQL queries, database design, normalization, ER diagrams, debugging, project documentation, and DBMS viva preparation.

When requesting support, share the assignment prompt, database platform, schema or ER diagram, attempted work, error or unexpected output, and expected result. Remove passwords, private credentials, and real sensitive information before sharing. Follow your institution’s academic-integrity policy and submit only work you understand and can explain.

### A quick review checklist

Before submitting your DBMS assignment, ask:

1. Does every important table have a primary key?
2. Do foreign keys represent the intended relationships?
3. Are many-to-many relationships modeled with junction tables?
4. Are repeated facts and normalization issues addressed?
5. Does each query have a clear result grain?
6. Have duplicate rows and aggregate totals been checked?
7. Have null, empty, and boundary cases been tested?
8. Does the SQL match the required database platform?
9. Does the documentation explain the design decisions?
10. Can you explain the project in your own words?

**Design carefully. Query deliberately. Test completely. Explain confidently.**
